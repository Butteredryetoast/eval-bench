# 旧版本地词面检索（RAG_ENGINE=local）

此文保留旧版词面检索的设计与当时验证记录。用户后续要求先在电脑测试 Haystack/FastEmbed，该实现与最新结果见 [Haystack RAG 说明](haystack-rag.md)；下文“未安装”等表述仅描述旧版本。

2026-10-27：按用户“只需要增强检索能力的部分”的范围，在现有 Node API 内完成检索增强。无需腾讯云 ES、WeKnora、独立数据库或新增 API 密钥。服务器部署已经取消，未重新操作服务器。

## 从热点到写作

`热点 + 用户粘贴的资料 → 当前 Obsidian 快照 → 主题/写法两路检索 → 合并、去重和结构分散 → DeepSeek 提供三个方向 → 用户确认 → 单次起草`

1. 每次查询继续通过原来的只读适配器检查新增、修改、删除；采用最高累计拆解版本，排除 2023 年前文章。来源缺失报错，绝不回退静态导出。
2. 原文、拆解、结构卡和方法笔记分成不超过 900 字符的段落窗口，交叠 120 字符，尽可能沿换行切分。长文的末尾也参与匹配。
3. 用中文分词、低权重双字补充、词频饱和及长度归一化做本地 BM25 排序。标题词频权重为 2。`k1=1.2`、`b=0.75`；这是项目自己的词项与字段策略，不声称与 ES 排序逐项等价。参数含义参见 [Elastic BM25 文档](https://www.elastic.co/docs/reference/elasticsearch/index-settings/similarity)。
4. 主题路读取热点描述，以及用户实际粘贴的资料标题、正文。描述最多 20,000 字符；前 100 条资料各取最多 500 字标题，正文按 12,000 字符总预算分配、单条最多 3,000。链接不抓取。每个字段内查询词重复不会增加权重；选择最多 160 个在索引里存在的信息词，不再只取开头 64 个字对。
5. 写法路读取已拆解文章的读者任务、适用选题、真实阶段及开头/中段/结尾说明。作者明确说“比较、怎么选”等才扩展对比选型词；“实测、教程、原理、影响、盘点、故事”等有各自规则。仅材料里出现“实测”不等于作者要求亲测。不把旧候选结构标签作为已验证的写法证据；缺料限制和负面边界不作为正向适配字段。 作者没有明确写作任务时，不启用写法召回通道；“围绕这条消息组织一篇文章”等通用指令不作为主题证据。
6. 先限定体裁，文章每路只保留最佳命中段落，各取最多 80 篇候选，再按 RRF 合并：每路排名贡献 `1/(60+rank)`，不直接相加两路 BM25 原始分数。参见 [Elastic RRF 文档](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)。相同融合分数才按复核等级、已拆解结构偏好和 ID 决定顺序。复核状态不能让零匹配文章入选。
7. 同一文章仅一个名额；优先分散结构，剩余名额仅从实际召回候选中补充。没有命中就返回空案例，不拿随机高质量文章填满 12 篇。结构定义独立匹配、排序，仍交给模型完整的当前体裁结构集合，避免只凭词面删掉可用结构。
8. 模型收到实际片段、命中词、主题/写法通道和候选状态。方向卡展开案例时显示这些依据；只命中写法会提示“主题可能不同”。排序分数不是准确率。确认方向后，起草最多带入 6 篇案例，只含该方向选中的案例或同结构的已拆解案例。

当前索引在进程内缓存。Vault 快照未变复用索引；快照变化后下次查询重建。不是后台云同步；大量频繁编辑时可能有重建开销。健康/模板刷新不预先构建全文索引。

## 接口与边界

- `/api/health` 的 `knowledge.retrieval` 和 `/api/library` 的 `source.retrieval` 表示已安装的检索策略，不代表知识库已读通或命中经过人工评价。
- 搜索和推荐返回 `retrieval.engine=local-bm25-rrf-v1`、`vectorSearch=false`、`modelCalls=0`。其中候选数是各路窗口中的数量，不是全库所有相关资料的计数。
- 搜索结果及推荐案例的 `match` 带真实命中词/通道/片段来源，网页保留 Obsidian 打开链接。实际正文片段和拆解片段仍区分。
- 生成事实仍只来自本次用户提供的材料。历史库仅作结构写法参考。Humanizer-zh 继续在同一次写作请求里生效。
- 当前属于词面检索加可解释任务词扩展，**没有安装 embedding、向量检索或神经重排模型**。不能保证识别所有同义转述，也不能自动证明素材充分、历史分类正确或三个方向就是最优解。即使 BM25 分数非零，也需要阅读案例判断是否适用。

## 验证记录与下一步

使用临时 Markdown Vault 和本地模拟模型的自动测试覆盖：正文/资料内容命中、深处段落、跨块词、长文去重、体裁过滤、旧候选标签隔离、跨话题写法、零匹配不补位、笔记编辑与删除后的索引失效、片段与来源链接、模型提示及单次调用。HTTP 测试已改用临时 Vault，避免依赖个人目录权限；没有修改或绕过真实库的权限。

规模检查使用 **5,858 条合成记录、约 331 万字符、1,000 条附带合成拆解**，初次建索引约 848 ms，一次热查询约 32 ms，当时 JS heap 约 40 MiB。这是重复主题的合成数据，仅检查基本资源开销，不代表实际库的性能或检索准确率。

初次读取真实 Vault 曾遭 macOS `EPERM` 拒绝。2026-10-27 用户完整重启 ChatGPT 后，读取权限恢复，正常 API 已重新连接。实际读取 5,858 篇文章、1,000 篇拆解、27 个结构、364 篇独立复核、11 篇方法笔记，无解析警告；唯一 ID 检查通过，未混入 2023 年前记录。

全库首次验收暴露了重复搜索文本的内存占用问题：删除内部未使用的归一化副本，将旧兼容搜索字段改为按需计算，并将倒排表压缩为整型数组。没有修改 Vault。随后在 1 GiB JS heap 上限的独立进程内完成全库建索引和 7 组检索检查，索引包含 51,618 个段落；冷查询（含建索引）约 15.5 秒，后续这组查询约 43–157 ms（含检查文件变化）。进程结束前 heapUsed 约 569 MiB、倒排表等 arrayBuffers 约 163 MiB、RSS 约 919 MiB。该记录是本机单次抽查，不是性能承诺。

真实库抽查包含智能体记忆、视频工具对比、知识库教程、上下文/记忆科普、产品演示的证据边界、仅靠引用正文匹配，以及不存在词返回零结果。命中示例包括视频模型选型实测、私有知识库部署教程、“家长群”的原文/拆解；体裁过滤及返回 ID 去重检查通过。输入是测试场景，不代表最新新闻；这些检查尚不是人工标注的准确率评测。结果保存在 `docs/qa/local-retrieval-live.json`。68 项自动测试通过，没有真实 DeepSeek 付费调用。

浏览器控制此前被 Work 设置禁用，未声称新增依据区域已经通过浏览器视觉复验。

下一步应选 20–30 个真实热点，人工标注可接受的案例与结构，在固定快照上比较旧版与新版的 Top3 可用率、Recall@12、错误入选、结构覆盖及耗时；另保留未参与调整的题目复验。只有出现可复现的同义漏召，再评估是否添加本地 embedding。这些评价尚未完成，不能把通过功能测试写成“准确率提升了某个百分比”。
