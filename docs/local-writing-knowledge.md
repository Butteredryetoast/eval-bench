# 本机写作知识库服务 · 2026-10-28

当前 Mac 暂时作为知识库服务器。网站写作板块已启用 `http://127.0.0.1:43130`，由服务端凭据访问本机检索桥接。当前前端布局、样式和交互没有改动。

## 结构匹配与大纲为同一阶段（2026-10-28）

用户确认的流程为：第一阶段同时匹配结构并给对应大纲、叙事动作、素材位置和引用；确认后才进入全文初稿。后端按本轮任务与已完成消息区分阶段，不再把“编辑器正文为空”当作完整初稿的判定。方向/大纲可以返回 reply 或 Markdown edit，不强求全文 narrative.plan/draft.blocks；全文阶段继续严格校验素材顺序与缺料依赖。每个阶段都必须先查知识库并返回引用。版本记录将大纲标为“结构与大纲”，不标成 AI 初稿。

Genie 4 的两次失败由旧空正文判定误拦大纲引起，知识库和模型均已正常返回。两份真实原始响应经新链路隔离回放，均按 planning 阶段插入大纲，并保留 2 篇知识库引用；没有额外模型调用，也没有覆盖正式文章。回放文件在 output/qa-two-stage-20261028/。历史失败提示不会自动改成成功记录。

## 生成前必查与引用交付（2026-10-28）

结构推荐、大纲、正文和修订现已强制先检索知识库并读入正文，不依赖用户提到“知识库”或要求“附引用”。连接关闭、不可用或没有可读来源时不调用写作模型。桥接返回命中文章与蓝图来源文章的安全元数据及正文，总正文预算 24,000 字符；长文会截取并用 contentScope/readChars/totalChars 明确记录范围。未拆解文章不会因 candidate 标记被禁止引用；该标记表示结构尚未完成拆解，不代表原文不存在。

同一次写作 JSON 中必须返回 knowledgeCitations，内容为 articleId、purpose、location、quote。后端验证 ID 确在本轮已读集合，短引文确实存在于已提供正文；采用的资讯蓝图来源、作为素材的 kb: 来源也必须列出。历史事实可引用，但保留报道日期和归属，不当作当前进展或作者亲历。引用有据不等于已对报道做外部事实核查。

后端附“本次知识库参考”，包含文章标题、原文链接、ID、拆解状态、日期、用途和对应短引文。正文使用稳定〔库:文章ID〕标记，由后端按实际对象编号，避免结构参考与事实参考排序不同导致错号；保留原链接已有百分号编码。结构讨论在助手回复末尾附录，全文写入正文末尾，选区/段落替换只在助手消息中附录，精确替换范围不混入参考列表。消息保存 consulted 与 citations 元数据，不在对话历史重复保存全文。伪造引用、引文不匹配或缺少引用的结果不写入正文，不自动重试模型。

真实验收使用没有“调用知识库”或“附引用”字样的 IPO 选题：事件顺序为检索→读完→生成，GPT-6.1-Terra 一次生成附 4 篇实际引用，含 APPSO 未拆解 IPO 正文。引用编号和编码链接用同一次原生响应回放验证，没有额外模型调用。隔离报告及验收稿在 output/qa-required-knowledge-20261028/；用户原稿未覆盖，前端、Vault 与现有模型索引未改动。

## 进程与配置

- 服务入口：`integrations/writing-retrieval/context-server.mjs`。
- 独立依赖：该目录的 `yaml` 已安装；使用该目录现有锁文件。
- 私有环境：`integrations/writing-retrieval/.env`，权限 0600；通过 Node 的 `--env-file` 加载。
- 网站连接配置：`.casebench/writing-knowledge.json`，权限 0600，已启用；令牌不会返回浏览器。
- 登录服务：`~/Library/LaunchAgents/local.eval-bench.writing-retrieval.plist`，标签 `local.eval-bench.writing-retrieval`；登录后启动，异常退出后重启，最多使用 2 个 ONNX 线程。
- 日志：`.casebench/logs/writing-retrieval.log` 和 `writing-retrieval.error.log`。

服务只监听本机回环地址，仅开放鉴权的 `/health` 与 `/context`。原写作站和原 Python 进程保持原状，索引写入继续使用现有跨进程锁。

这不是公网连接验收。网站以后搬到其他电脑或云端时，`127.0.0.1` 会指向网站所在主机，届时应通过私人网络或隧道把检索请求送回当前 Mac，再更新网站保存的服务地址。知识库、向量索引、模型仍可留在本机。当前没有改动任何远端服务器或开放公网端口。

Mac 需保持开机、登录且不休眠；关闭笔记本或休眠期间无法提供检索。重启后登录会恢复服务；未启用阻止睡眠等系统级设置。

本次修复了蓝图投影漏字段：原桥接把 `name` 当成不存在的 `title`，并丢掉节点内 `beats`，素材的作用、顺序与依赖因而没有传给写作端。现在保留标题、版本、读者问题、叙事动作、承接，以及有序的叙述／素材／观察／转场片段；素材类型、必要性和依赖保持原值。本地文件路径和 Obsidian 地址仍不向写作模型发送。

这些字段向当前写作模型提供叙事参考；本次没有修改现有编辑器或引入旧站的强制生成渲染协议，不能据此保证模型成稿质量或每个素材位置都自动遵守。

# 资讯素材位修复 · 2026-10-28

## 续写检索的选题继承

`writingKnowledge` 此前直接使用当前一句话检索，第二轮“选择2，两千字左右……”因此丢失 Anthropic IPO 选题。现在检索请求从本篇文章继承标题、最初用户选题、已选方向和有限的用户补充，再加入本轮要求；不会把生成正文整体当作检索主题。方向只取用户选择的那一项，后续短指令保留选择；新建文章不继承其他文章的内容。体裁沿用最近一次明确要求，新要求可以覆盖。请求总长度受限，已有引用开关和移除状态继续生效。字数与“第三季度”等普通数字不会被当成方向选择。

该修复只调整本地检索请求，不增加生成或润色模型调用。真实检索对照与脚本保存在 `output/qa-retrieval-context-20261028/`；原文、已有稿件及前端未改动。

真实 Haystack 检索复测第一条为 APb6693e72f391《Anthropic 秘密申请 IPO，一边抢跑一边防着OpenAI》（候选记录），后续包含 Anthropic、Claude 及相关公司战略文章。本次请求已保留原选题和选中的 N3 方向，未调用写作模型；50 项项目测试及类型检查通过。首次真实查询在 120 秒内未返回，检查服务就绪后再次查询用时约 49.9 秒成功；结果证明本次查询修复，不代表检索延迟已经优化，也不把命中文章当作本次新闻的已核实事实。

此前只把蓝图 JSON 拼入写作提示，没有调用原项目的叙事计划校验与渲染；同时“不要输出媒体占位符”的提示没有区分已有附件与缺失证据。因此正文能生成，素材节点和缺料依赖却未得到执行。

资讯全文初稿现在在同一次模型回复中返回 `narrative.plan` 与 `narrative.draft.blocks`。主站复用原 `compileNewsPlan` / `renderNewsDraft`，校验节点、素材绑定、当前引用 ID、片段顺序和缺料依赖，并在实际节点插入 `【素材位：…】` 与 `【待写：…】`。材料包括事实、引语、数据和案例，不限图片视频。资料完整时不人为增加占位符；缺料时不要求凑满目标字数。待写说明使用针对本次选题的叙事任务，避免把旧文章段号与原作者背景抄进稿件。

完成结构与大纲并进入全文初稿阶段后，资讯稿不带叙事计划则不写入正文，也不自动追加模型重试。结构匹配和大纲为第一阶段，用 Markdown 并校验引用，不要求全文叙事计划；其他体裁和已有正文的局部修改继续使用相应协议。人工正文与媒体卡保留既有版本和修订流程；前端未改动，知识库及索引未改动。

验收使用用户同一 IPO 选题与原先第二方向：真实 GPT-6.1-Terra 返回了完整计划及片段；同一次原生响应经正式 EditorialService 回放，在空白正文中保存了 5 个素材位和 5 个待写节点，无额外模型调用。第一次验收夹具未建立空白正文，把历史方向讨论当成正文，因此只查看正文时误报了零素材位；修正夹具后验证了实际插入路径。原始响应、验收稿、报告和脚本位于 `output/qa-narrative-20261028/`，均为隔离验收，没有覆盖用户文章。
